# Яагаад ийм байдлаар барьж байгаа вэ

Энэ файл бол шийдвэрийн бүртгэл. Код өөрчлөгдөнө — шалтгаан нь үлдэнэ.

## Асуудал

AI-д зориулсан preview sandbox. Гаднын хүмүүс өөрийн кодоо ажиллуулж
болдог тусгаарлагдсан орчин.

Бидэнд **SAND** (github.com/Zulzaga0428/SAND) гэдэг ажиллаж байгаа систем
бий. Энэ төсөл түүнд **огт хүрэхгүй**.

## Гол сургамж: SAND яагаад гацсан бэ

SAND-ийн `controller/sandbox.js` нь 2185 мөр. Түүн дотор dockerode-ийн
дуудлага **40 гаруй газар** тархсан: `putArchive`, `getArchive`,
`exec` урсгалын 8 байтын multiplex толгой, `demuxStream`, `HostConfig`,
`HostPort`.

Хэн ч үүнийг санаатай хийгээгүй. Өдөр бүр нэг мөрөөр нэмэгдсэн.

Үр дүн: **runtime нь солигддог давхарга биш, бүтээгдэхүүний суурь болсон.**
2026-09-20-нд gVisor руу шилжих боломжтой эсэхийг хэмжихэд техникийн
хувьд боломжтой байсан ч, кодын хувьд боломжгүй байв.

Тиймээс энэ төсөлд эхний өдрөөс:

```
интерфейс → FakeRuntime → бүх логик → жинхэнэ runtime ХАМГИЙН СҮҮЛД
```

Мөн энэ нь **сануулга биш, тест**: `test/no-leak.test.ts` нь
`src/runtime/`-аас гадуур `dockerode`, `firecracker`, `putArchive`,
`/dev/kvm` гэж дурдвал улаан болно. Учир нь «бичсэн сануулга нь засвар биш»
гэдгийг бид SAND дээр аль хэдийн төлсөн.

## Runtime-ийн сонголт: Firecracker

**Шийдвэр:** Firecracker (microVM). gVisor биш.

### Хэмжсэн баримт (2026-09-20, прод төмөр дээр)

| шалгуур | runc | runsc (gVisor) |
|---|---|---|
| bind mount дахь файл харагдах | ✅ 113ms | ✅ 79ms |
| **inotify** (fs.watch) | ✅ 5 event | 🔴 **0 event** |
| polling (fs.watchFile, 300ms) | ✅ 110ms lag | ✅ 280ms lag |

### Яагаад Firecracker

1. **Нийцтэй байдал.** gVisor нь Linux-ийн syscall-уудыг Go дээр дахин
   бичсэн. Node, Bun, Next-ийн шинэ хувилбар бүр эрсдэл. Бид үүнийг аль
   хэдийн амссан — inotify тэг. Firecracker-ийн доор жинхэнэ Linux цөм.
2. **Аюулгүй байдлын гадаргуу.** Гаднын код ажиллуулах нь бүх зорилго.
   Firecracker = KVM ioctl + 5 төхөөрөмж, AWS Lambda-гийн хэмжээнд
   аудитлагдсан. Нийцтэй байдлын цоорхой нь өөрөө аюулгүй байдлын
   гадаргуу гэдгийг бас тооцов.
3. **Хүндийн хүч.** Lambda, Fargate, Fly.io, E2B, Modal, Northflank —
   бүгд microVM дээр. Хүн, хэрэгсэл, нүүх зам бүгд тэнд.

### Firecracker-ийн үнэ (эхний өдөр мэдэж байх ёстой)

- **`/dev/kvm` шаардана.** Vultr VPS дээр БАЙХГҮЙ (VPS өөрөө VM). Windows
  10 WSL2 дээр ч БАЙХГҮЙ (Win11-д л нэмэгдсэн). Туршихад GCP/Azure-ийн
  nested virtualization VM. Прод дээр bare metal (~$120-200/сар).
- **virtio-fs БАЙХГҮЙ.** Зориуд. Firecracker-ийн төхөөрөмжүүд: block,
  net, vsock, rng, balloon, консол. Файлын систем хуваалцах сервер нь
  гадаргууг томсгоно гэж үзээд p9-г ч татгалзсан.
  → **«bind mount» гэсэн загвар Firecracker дээр ОГТ БАЙХГҮЙ.**
  → Ажиллаж буй VM руу файл оруулах зам: vsock дээрх зочин доторх агент,
    эсвэл ачаалахын өмнө ext4 образ. E2B, Fly хоёр яг ийм агенттай.
- **`docker exec` гэж байхгүй.** Мөн тэр агентаар л биелнэ.

Энэ нь Firecracker-ээс татгалзах шалтгаан биш — харин runtime-ийг
интерфейсийн ард нуух шийдвэрийг улам зөв болгож байна. Эдгээр ялгаа
бүгд **нэг файлыг** хөндөнө.

## Хэрэгжүүлэлтийн эрэмбэ

```
1. FakeRuntime        санах ойд        тест, $0          ✅ бэлэн
2. DockerRuntime      ямар ч Linux     өнөөдөр, $0       ✅ 32/32 жинхэнэ Docker
3. FirecrackerRuntime bare metal       мөнгө орсны дараа ⬜
```

### DockerRuntime-ийн файл дамжуулалт: bind mount, `putArchive` БИШ

SAND нь ажиллаж буй контейнер руу `putArchive` хийдэг. Тэр нь gVisor дээр
чимээгүй унадаг бөгөөд SAND-ыг gVisor дээр ажиллуулах боломжгүй болгосон
гол шалтгаан байв. Bind mount дээр энэ асуудал ОГТ гардаггүй — host дээрх
хавтсанд бичихэд дотор шууд харагдана (2026-09-20: runc 113ms, runsc 79ms).

Нэмэлт ашиг: Workspace нь контейнерээс тусдаа амьдарна — контейнер
унтарсан ч файлууд байрандаа. Интерфейсийн гэрээ яг үүнийг шаарддаг.

⚠️ Bind mount нь controller болон Docker daemon нэг файлын систем
хуваалцаж байхыг шаардана. Vultr дээр үнэн (нэг хост).

Docker яагаад дунд нь байна вэ: **нэг хэрэгжүүлэлтээр батлагдсан
интерфейс нь батлагдаагүй.** Хоёр дахь нүд орж ирэхэд л хийсвэрлэл
жинхэнэ эсэх нь мэдэгдэнэ. Бас энэ нь Firecracker-ийг хүлээлгүйгээр
өнөөдөр ажиллаж байгаа зүйл өгнө.

## Runtime-аас хамаарахгүй хэсгүүд

Ажлын ихэнх нь энд байгаа бөгөөд эдгээр нь VMM солигдоход **амьд үлдэнэ**:

файл дамжуулалт · дулаан сан · preview домэйн + wildcard TLS + чиглүүлэлт ·
TTL/keepalive/чөлөөлөлт · хэмжигч · алдааны гэрээ · багтаамжийн хаалт

10 жил наслах хөрөнгө бол runtime биш, **энэ жагсаалт ба интерфейс**.

### `PreviewManager` дээр SAND-ийн 4 алдааг хэрхэн хаасан

**1. Слот нь `await`-аас ӨМНӨ синхроноор нөөцлөгдөнө.** `create()` дотор
доод давхарга руу хандах `await` бий. Багтаамжийг зөвхөн бүртгэлийн
хэмжээгээр шалгавал зэрэг ирсэн 8 хүсэлт бүгд «сул байна» гэж уншаад
хязгаарыг давна — SAND-ийн жинхэнэ алдаа. Тест: 8 зэрэгцээ хүсэлт,
хязгаар 2 → яг 2 амжилттай.

**2. `expired` ба `vanished` ТУСДАА тоологдоно.** «Бид чөлөөлсөн» ба
«доод давхаргаас алга болсон» хоёр тэс өөр зүйл. SAND-д нэг тоонд
нийлж, «preview яагаад үхэв» гэдэг хариугүй болдог байв.

**3. `stats.oomKilled` нь `number | null`.** `caps.memoryLimit === false`
бол `null` — «OOM болоогүй» гэсэн үг БИШ, «хэмжиж чадахгүй» гэсэн үг.
`0` гэж хэвлэвэл самбар худал болно. SAND яг ингэж хуурсан.

**4. Хугацаа нь `Clock`-оор орно.** Тест жинхэнэ секунд хүлээхгүй тул
TTL-ийн логик найдвартай хэмжигдэнэ. `setTimeout`-оор хүлээдэг тест нь
машины ачааллаас хамаарч хэлбэлздэг — тэр нь дохио биш шуугиан.

### `getWorkspace` — дээд давхаргыг барихаар суухад илэрсэн цоорхой

`Runtime`-д `createWorkspace()` байсан, `getWorkspace()` байгаагүй.

Утга: controller дахин эхлэхэд машиныг `get()`-ээр олж чадна, гэхдээ
түүний **файлууд руу хүрэх зам байхгүй** → preview тахир дутуу сэргэж,
файл шинэчлэх боломжгүй болно. SAND-д «restart-д preview үхэхгүй» чанар
байсан; энэ интерфейс түүнгүйгээр тэр чанарыг биелүүлж чадахгүй байв.

📌 Интерфейсийн цоорхой нь интерфейсийг уншаад олдоогүй — түүн дээр
**жинхэнэ зүйл барих гэж суухад** олдсон.

### Механик хамгаалалт миний өөрийн файлыг барив

`src/manager/preview.ts`-ийн тайлбарт «firecracker» гэж бичсэнээр
`no-leak.test.ts` улаан болов. Хамгаалалтыг сулруулаагүй — тайлбарыг
өөрчилсөн. Нэр дурдах эрх нь `src/runtime/` дотор л бий.

## SAND дээр өвдөж сурсан 4 дүрэм

Эдгээр нь зөвлөмж биш — интерфейсийн гарын үсэгт шингэсэн:

| дүрэм | хаана шингэсэн |
|---|---|
| **Харж чадахгүй зүйлийг «0» гэж бүү хэвлэ.** SAND-ийн `oomKilled` зөвхөн create-ийн үед тоологдож, ажиллаж байхад алагдсан барилтууд хэдэн долоо хоног үл мэдэгдэв. Самбар «OOM 0» гэж байхад хэрэглэгчийн ажил үхэж байсан. | `status()` хэзээ ч кэшлэгдэхгүй · `state: "gone"` нь `"exited"`-ээс тусдаа · `exitCode` нь мэдэгдэхгүй үед `null`, 0 биш · `caps.memoryLimit=false` үед `oomKilled` нь «болоогүй» биш «хэмжиж чадахгүй» |
| **Бичсэн сануулга нь ЗАСВАР БИШ.** `MAX_FILES=50` бага гэж баримтад бичээд утгыг нь сольсонгүй; сарын дараа жинхэнэ хэрэглэгчид дээр буув. | `no-leak.test.ts` — сануулгын оронд улаан тест · `timeoutMs`, `maxOutputBytes` нь өгөгдмөл утгагүй, **заавал** |
| **Алгасалт нь амжилт гэж уншигдах ЁСГҮЙ.** | `WriteResult.rejected` — хэсэгчилсэн амжилтыг нэрлэнэ · hook байхгүй тест нь чимээгүй ✅ биш, `t.diagnostic`-оор ил тэмдэглэнэ |
| **Дохио бүр улаан болж чаддагийг батал.** | `test/fake.test.ts` → «мутацийн сорил» · `FakeWorld` нь OOM, timeout, алга болох, квот бүгдийг зориуд үүсгэнэ |

Мутацийн сорил 2026-09-30-нд гүйцэтгэгдэв:

| гажуудал | үр дүн |
|---|---|
| замын хамгаалалт унтраав | 12 тест улаан |
| алга болсныг үл тоов | 3 тест улаан |
| OOM-ыг үргэлж false болгов | 2 тест улаан |
| сэргээв | 76/76 ногоон |

## Хоёр дахь хэрэгжүүлэлт юу гаргаж ирэв (2026-10-01)

Docker-ийг Firecracker-ээс өмнө хийсэн шалтгаан нь яг үүнд байв —
**нэг хэрэгжүүлэлтээр батлагдсан интерфейс нь батлагдаагүй.**

Жинхэнэ Docker дээрх анхны ажиллалт: **32/33**. Унасан нь:

```
not ok - байхгүй id дээр get нь null
  error: 'Request path contains unescaped characters'
```

`get()` нь Docker-ийн id биш мөрийг шууд dockerode-д дамжуулж байв.
dockerode түүнийг URL болгож чадалгүй **шиддэг** — 404 биш. Гэрээ нь
«байхгүй id дээр null» гэж шаарддаг тул шидэж болохгүй.

FakeRuntime дээр ямар ч id ажилладаг тул **энэ алдаа хэзээ ч
харагдахгүй байсан.** Firecracker хүртэл хүлээсэн бол ижил алдаа тэнд
дахин гарах байв.

Хоёр дахь олдвор: `forceOom(rt, m)` гэсэн hook нь Docker дээр ажиллах
боломжгүй байв. Docker-т `exec`-ийн хүү процесс алагдахад контейнерийн
`State.OOMKilled` тавигддаггүй — зөвхөн **үндсэн** процесс алагдахад
тавигддаг. Тиймээс `oomMachine(rt)` болгож сольсон: OOM-д зориулж тусдаа
машин үүсгэх нь цорын ганц найдвартай арга.

## Батлалтын хэрэгсэл: GitHub Actions, сервер БИШ

DockerRuntime-ыг батлахад Docker-той Linux хост хэрэгтэй — **сервер биш.**
Actions-ийн runner дээр Ubuntu + Docker бэлэн ирдэг, үнэгүй.

📌 Vultr руу SSH хийх зөвшөөрөл гуйх нь **шаардлагагүй байсан.**
«Docker дээр батлах» ≠ «сервер дээр батлах».

⚠️ GitHub-ийн лог ба ажлын хураангуй хоёулаа JS-ээр ачаалагддаг тул
гаднаас автоматаар уншигдахгүй. Тестийн гаралтыг `::error::`/`::notice::`
тэмдэглэгээгээр гаргадаг болсон — тэр нь checks API-д нээлттэй байдаг.

## Юу БАТЛАГДААГҮЙ вэ (2026-10-01)

Энэ хэсэг санаатай байна. «Харж чадахгүй зүйлийг 0 гэж бүү хэвлэ» дүрэм
кодод төдийгүй баримтад ч хамаарна.

- **`logs().truncated`** нь таамаг: `tail`-ийн хэмжээнд хүрсэн эсэхээр
  дүгнэнэ. Docker API нь «илүү мөр байсан уу» гэдгийг хэлдэггүй.
  Гэрээнд `logs()`-ийн тест ОГТ БАЙХГҮЙ — энэ нь нээлттэй цоорхой.
- **`caps.diskQuota: false`** — Docker-ийн `StorageOpt` нь зөвхөн тодорхой
  storage driver дээр ажиллана. Хэмжээгүй тул «боломжгүй» гэхээс
  «мэдэхгүй» гэж тавьсан.
- **Дулаан сан, TTL, чиглүүлэлт, багтаамжийн хаалт** — нэг ч мөр бичээгүй.
  Ажлын ихэнх нь эндээ байна.
